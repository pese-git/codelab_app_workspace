# План реализации UI-реплики OpenCode Desktop

## Цель

Воспроизвести UI приложения `reference/opencode` внутри `apps/codelab_desktop` на Flutter SDK с использованием библиотеки `fluent_ui`.

Целевой результат на этом этапе:

- повторить все основные виджеты
- повторить переиспользуемые компоненты
- повторить навигацию
- повторить экраны
- повторить диалоги
- повторить overlay-поверхности
- повторить ключевые layout-состояния

На первом этапе фокус на desktop UI и интерактивном прототипе. Данные могут быть моковыми, но архитектура должна быть пригодна для последующего подключения реального backend/state layer.

## Источники истины

Основные reference-пути:

- `reference/opencode/packages/app/src`
- `reference/opencode/packages/desktop/src`
- `reference/opencode/packages/ui/src`

Примечания:

- `packages/app/src` содержит основную структуру приложения, страницы и UI-логику.
- `packages/desktop/src` содержит desktop-обвязку и платформенные интеграции.
- `packages/ui/src` содержит переиспользуемые UI-примитивы и визуальный язык приложения.

## Ожидаемый результат

Итогом должен стать Flutter desktop-прототип в `apps/codelab_desktop`, который воспроизводит опыт использования OpenCode Desktop, включая:

1. домашний экран
2. левый rail со списком проектов
3. sidebar со workspace/session-структурой
4. основной экран сессии
5. title bar и верхние элементы управления
6. область prompt composer
7. регионы file/review/terminal
8. правую контекстную панель
9. диалоги и вторичные overlay-поверхности

## План работ

### 1. Аудит reference UI

Цель: извлечь полную карту интерфейса из OpenCode reference.

Задачи:

- собрать список всех основных экранов и подэкранов
- собрать список всех диалогов, popover-элементов и overlay-поверхностей
- собрать список всех навигационных переходов и состояний выбора
- выделить переиспользуемые визуальные примитивы и повторяющиеся layout-паттерны
- задокументировать состояния empty, loading, active, expanded, disabled

Ожидаемый результат:

- карта экранов и компонентов для Flutter-реализации
- матрица состояний по ключевым UI-поверхностям

### 2. Проектирование Flutter-архитектуры

Цель: заранее определить устойчивую структуру приложения.

Задачи:

- создать структуру папок в `lib/`
- развести shell, экраны, диалоги, виджеты, тему и mock-модели
- определить app-level navigation и selection state
- определить mock-сущности для проектов, workspace, sessions, messages, tabs и dialogs
- зафиксировать соглашения по именованию, согласованные с понятиями OpenCode

Ожидаемый результат:

- чистая структура Flutter-проекта
- единая модель состояния, готовая к последующей интеграции с реальными данными

### 3. Тема и desktop shell

Цель: воспроизвести основной desktop-каркас и визуальную базу приложения.

Задачи:

Ожидаемый результат:

### 4. Основные экраны

## Риски и замечания

### Риск объема

UI OpenCode довольно широкий. Формулировка "полностью воспроизвести" включает большое количество состояний, диалогов и вспомогательных поверхностей, поэтому реализация должна идти по слоям, а не одним большим файлом.

### Риск точности

Часть визуального поведения OpenCode опирается на кастомные web UI-примитивы и desktop-специфику. Во Flutter нужно повторить layout и поведение максимально близко, но при этом оставаться в рамках идиоматичного использования `fluent_ui`.

### Риск интеграции

Если слишком рано перейти к реальному backend wiring, скорость сборки UI заметно упадет. Рекомендуемая последовательность такая:

1. mock UI parity
2. интерактивная связка состояний
3. интеграция с backend

## Ближайший следующий шаг

1. восстановить `main.dart`
2. создать app-структуру внутри `lib/app`

5. поэтапно собрать home и session surfaces
